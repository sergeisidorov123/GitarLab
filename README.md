## Что делает проект?

**Guitar Lab** — это веб-приложение для музыкантов, которое включает:

- **гитарный тюнер** (устройство, которое показывает, насколько струна настроена);
- **каталог треков** с информацией о песнях и тюнингах;
- **пользовательскую библиотеку** треков;
- **систему регистрации и входа**;
- **систему комментариев** под треками;
- **панель администратора** для удаления комментариев.

Все эти компоненты работают вместе через сеть. Пользователь открывает браузер, а браузер общается с разными сервисами.

---

## Что такое микросервисы?

Вместо одной большой программы в проекте несколько небольших приложений, которые делают своё дело.

Каждый сервис:

- выполняет строго определенную задачу;
- работает независимо от других сервисов;
- может запускаться отдельно;
- может быть перезапущен без остановки всей системы.

В нашем проекте есть четыре основных сервиса:

1. `tuner-service` — тюнер;
2. `catalog-service` — каталог треков и тюнингов;
3. `user-service` — регистрация, авторизация и треки пользователя;
4. `comment-service` — комментарии к трекам.

И плюс фронтенд (`frontend`) — то, что видит пользователь.

## Что такое Docker и Docker Compose?

### Docker

**Docker** — это инструмент, который позволяет упаковать программу вместе со всеми её библиотеками и настройками в единый «контейнер».

Контейнер похож на маленький виртуальный компьютер, на котором запускается только одно приложение.

### Docker Compose

**Docker Compose** — это специальный файл (`docker-compose.yml`), в котором описывается, какие контейнеры нужно запустить вместе.

В нашем случае `docker-compose.yml` говорит Docker:

- запусти базу данных PostgreSQL;
- запусти `tuner-service`;
- запусти `catalog-service`;
- запусти `user-service`;
- запусти `comment-service`;
- запусти frontend.

Это очень удобно: не нужно запускать каждое приложение вручную.

## Объяснение терминов

### HTTP

**HTTP** — это протокол, по которому браузер общается с сервером.

Когда вы вводите адрес веб-страницы, браузер отправляет запрос на сервер, а сервер возвращает страницу.

В проекте фронтенд делает HTTP-запросы к backend-сервисам:

- получает список треков;
- отправляет логин и пароль;
- добавляет трек в избранное;
- получает комментарии.

### WebSocket

**WebSocket** — это способ общения между браузером и сервером, который позволяет поддерживать постоянное соединение.

Если HTTP работает как «запрос-ответ» (браузер спросил, сервер ответил), то WebSocket действует как открытый канал:

- сервер и клиент могут отправлять сообщения друг другу в любое время;
- это удобно для данных, которые меняются быстро;
- это подходит для тюнера, потому что звук обрабатывается в реальном времени.

В нашем проекте `tuner-service` использует WebSocket для постоянного обмена звуком и результатами.

### Авторизация и аутентификация

- **Аутентификация** — это процесс, когда система проверяет, кто вы. Обычно это логин и пароль.
- **Авторизация** — это процесс, когда система проверяет, что вам разрешено делать.

Пример:

- вы вводите логин и пароль (аутентификация);
- система говорит, что вы — пользователь;
- затем проверяется, можете ли вы удалять комментарии (авторизация).

### Токен

**Токен** — это строка, которая обозначает вашу сессию после входа.

Когда пользователь успешно логинится, сервер создает токен и возвращает его браузеру.

Токен запоминается в браузере и отправляется на сервер при каждом запросе, где нужна защита.

В нашем проекте токен хранится в базе `user-service` и используется услугой `comment-service` для проверки, что запрос действительно пришел от авторизованного пользователя.

### Хеширование пароля

Пароль пользователя нельзя хранить в базе в открытом виде. Вместо этого создается **хеш пароля**.

Хеш — это результат математической функции, из которого невозможно восстановить исходный пароль.

В проекте для хеширования используется PBKDF2 через `app.core.security.py`.

## Общая архитектура проекта

```
Browser (React)
  |     |     |     |
  |     |     |     +-- WebSocket --> tuner-service
  |     |     +-------- HTTP --> catalog-service
  |     +--------------- HTTP --> user-service
  +-------------------- HTTP --> comment-service

Инфраструктура:
postgres-db (PostgreSQL)
```

### Как это работает на практике

1. Пользователь открывает браузер на `http://localhost:3000`.
2. Фронтенд загружает страницу и может сразу делать запросы к backend.
3. Для входа пользователь отправляет логин и пароль на `user-service`.
4. `user-service` проверяет пароль, создает токен и возвращает его.
5. Браузер сохраняет токен и использует его при запросах к `user-service` и `comment-service`.
6. Если пользователь открывает экран тюнера, фронтенд подключается к `tuner-service` по WebSocket.
7. Когда пользователь играет на гитаре, звук с микрофона постоянно передается на `tuner-service`.
8. `tuner-service` обрабатывает звук и отправляет обратно результат: частоту и рекомендованную ноту.

## Детальный обзор сервисов

### 1. `tuner-service`

**Папка:** `services/tuner-service`

Это сервис для обработки звука и вывода результата в реальном времени.

#### Что происходит шаг за шагом

1. Пользователь нажимает кнопку «Старт» в браузере.
2. Браузер запрашивает разрешение на микрофон.
3. Если разрешение получено, браузер начинает собирать аудио-данные.
4. Эти аудио-данные отправляются на сервер по соединению WebSocket.
5. Сервер обрабатывает данные, находит частоту звукa.
6. Сервер высчитывает, какая нота наиболее близка к этой частоте.
7. Сервер отправляет обратно данные: частота, нота, отклонение, рекомендация.
8. Браузер отображает результат.

#### Почему WebSocket?

- потому что звук приходит непрерывно;
- потому что браузер должен быстро отправлять данные и получать ответы;
- потому что HTTP каждое сообщение обрабатывает как отдельный запрос,
  а WebSocket держит одно длительное соединение.

#### Основные файлы

- `app/main.py` — точка входа сервиса, подключает WebSocket.
- `app/config.py` — настройки сервиса.
- `app/models/schemas.py` — форматы данных, которыми обменяется сервис.
- `app/detectors/pitch_detector.py` — определение частоты звука.
- `app/detectors/note_finder.py` — определение ноты по частоте.
- `app/websocket/manager.py` — управление подключениями.

#### Как работает тюнер технически

- Сервер получает пакет аудио-данных.
- Детектор частоты `PitchDetector` анализирует цифровой сигнал.
- `NoteFinder` выбирает ближайшую ноту и считает отклонение в центах.
- Если струна ближе всего к ноте, сервер сообщает, где надо крутить колок.

### 2. `catalog-service`

**Папка:** `services/catalog-service`

Сервис предоставляет информацию о треках и стандартных настройках гитары.

Он умеет:

- возвращать список всех треков;
- создавать новый трек;
- выдавать данные конкретного трека;
- отдавать список доступных тюнингов.

#### Что такое тюнинг?

Тюнинг — это набор нот и соответствующих частот для шести струн гитары.

Пример:

- стандартный тюнинг: `E A D G B E`;
- `Drop D`: `D A D G B E`.

#### Таблицы в базе данных

- `tunings` — хранит название тюнинга, названия струн и частоты.
- `songs` — хранит треки с указанием, какой тюнинг им соответствует.

#### Стартовые данные

При первом запуске сервис автоматически создает:

- 7 стандартных пресетов тюнингов;
- 2 демонстрационных трека.

#### Основные файлы

- `app/main.py` — запускает приложение и создает данные.
- `app/core/config.py` — настройки сервиса.
- `app/core/database.py` — подключение к базе PostgreSQL.
- `app/models/song.py` — модель трека.
- `app/models/tuning.py` — модель тюнинга.
- `app/repos/song_repos.py` — работа с треками в базе.
- `app/repos/tuning_repos.py` — работа с тюнингами.
- `app/services/song_service.py` — бизнес-логика для треков.
- `app/api/songs.py` — HTTP-эндпоинты для треков.
- `app/api/tunings.py` — HTTP-эндпоинты для тюнингов.

#### Как работает создание трека

Когда приходит запрос на создание трека с `tuning_name`:

- сервис проверяет, есть ли такой тюнинг;
- если нет, то создает стандартный `Standard`;
- затем сохраняет трек с указанием `tuning_id`.

### 3. `user-service`

**Папка:** `services/user-service`

Это сервис, который отвечает за работу с пользователями и их треками.

#### Что делает этот сервис

- создаёт нового пользователя;
- принимает логин и пароль;
- проверяет пароль;
- выдаёт токен после успешного входа;
- хранит треки, которые добавляет пользователь;
- хранит жанры и любимые треки.

#### Почему здесь хранятся треки?

Потому что треки принадлежат пользователям. Этот сервис знает, кто создал трек, поэтому он управляет правами доступа.

#### Структуры в базе данных

- `users` — сами пользователи;
- `roles` — роли, например `user` и `admin`;
- `tokens` — авторизационные токены;
- `tracks` — треки, созданные пользователями;
- `genres` — жанры музыки;
- `track_genres` — связь трека и жанра;
- `favorites` — избранные треки пользователя.

#### Как работает регистрация и вход

1. Пользователь отправляет `username` и `password`.
2. Сервис проверяет, свободно ли имя пользователя.
3. Если имя свободно, пароль преобразуется в хеш.
4. Хеш хранят в базе, сам пароль не хранится.
5. На входе сервис сравнивает хеши.
6. Если пароль правильный, сервис создает **токен**.
7. Этот токен возвращается клиенту.

#### Как работает токен

- токен — это случайная строка;
- он сохраняется в таблице `tokens` вместе с пользователем;
- браузер сохраняет токен и отправляет его при каждом защищенном запросе.

#### Почему это безопаснее, чем хранить пароль?

- пароль никогда не хранится в базе;
- токен можно легко отменить;
- если кто-то получит токен, он сможет действовать от имени пользователя, но нельзя узнать сам пароль.

#### Роли пользователей

Есть две роли:

- `user` — обычный пользователь;
- `admin` — администратор.

Администратор может:

- назначать других пользователей администраторами;
- выполнять действия, запрещенные обычным пользователям.

#### Функции сервиса

- регистрация: `POST /auth/register`;
- вход: `POST /auth/login`;
- проверка текущего пользователя: `GET /auth/me`;
- создание админа: `POST /auth/make-admin/{user_id}`;
- управление треками: `GET /tracks/`, `POST /tracks/`, `PUT /tracks/{track_id}`, `DELETE /tracks/{track_id}`;
- избранное: `POST /tracks/{track_id}/favorite`, `DELETE /tracks/{track_id}/favorite`;
- жанры: `GET /genres/`.

#### Основные файлы

- `app/main.py` — запуск приложения и начальная инициализация;
- `app/config.py` — настройки сервиса;
- `app/core/database.py` — подключение к базе;
- `app/core/security.py` — хеширование паролей и генерация токенов;
- `app/models/user.py` — модель пользователя;
- `app/models/track.py` — модель трека;
- `app/models/genre.py` — модель жанра;
- `app/models/track_genre.py` — связь трека и жанра;
- `app/models/favorite.py` — модель избранного;
- `app/repos/user_repos.py` — запросы к таблицам пользователей и ролей;
- `app/services/auth_service.py` — логика регистрации и логина;
- `app/api/auth.py` — эндпоинты авторизации;
- `app/api/tracks.py` — эндпоинты треков.

### 4. `comment-service`

**Папка:** `services/comment-service`

Этот сервис отвечает за комментарии к трекам.

#### Что делает

- сохраняет комментарии пользователей;
- позволяет редактировать собственные комментарии;
- позволяет удалять собственные комментарии;
- показывает комментарии для конкретного трека;
- админ может получить все комментарии и удалить любой.

#### Почему здесь есть проверка `user-service`?

`comment-service` сам не хранит пользователей и пароли.

Он доверяет `user-service` и использует его только для проверки токена:

- когда приходит запрос, `comment-service` отправляет токен в `user-service`;
- `user-service` отвечает, кто это такой;
- `comment-service` принимает решение, можно ли выполнять действие.

Это называется **межсервисной аутентификацией**.

#### Таблица комментариев

- `id` — уникальный номер комментария;
- `content` — текст комментария;
- `author_id` — id пользователя, который написал комментарий;
- `author_username` — имя пользователя;
- `track_id` — id трека, к которому относится комментарий;
- `parent_id` — если комментарий отвечает другому комментарию;
- `created_at`, `updated_at` — время создания и изменения;
- `is_deleted` — флаг мягкого удаления.

#### Что такое мягкое удаление?

Если пользователь удаляет комментарий, он не обязательно полностью исчезает из базы.

Вместо этого в записи ставится `is_deleted = true`.

Такой подход позволяет:

- сохранить историю;
- дать админу возможность увидеть удаленные комментарии;
- избежать потери данных.

#### Основные файлы

- `app/main.py` — запуск сервиса;
- `app/config.py` — настройки;
- `app/core/database.py` — подключение к базе;
- `app/models/comment.py` — модель комментария;
- `app/repos/comment_repo.py` — работа с комментариями в базе;
- `app/services/comment_service.py` — бизнес-логика комментариев;
- `app/api/comments.py` — эндпоинты для пользователей;
- `app/api/admin.py` — эндпоинты для администратора;
- `app/api/auth.py` — проверка токена через `user-service`.

## Фронтенд: что видит пользователь

**Папка:** `frontend/`

Это React-приложение.

Фронтенд — это то, что работает внутри браузера и показывает интерфейс пользователю.

### Главные экраны

- `Тюнер` — интерфейс для настройки гитары;
- `Библиотека тюнингов` — список треков, поиск, создание и управление треками;
- `Track Page` — подробная страница трека с настройками и комментариями;
- `Админ` — панель для модерации комментариев.

### Как фронтенд общается с backend

Фронтенд использует два способа связи:

1. **HTTP-запросы** — для обычных операций (получение треков, логин, комментарии);
2. **WebSocket** — для отправки и получения звукoвых данных тюнера.

### Основные файлы

- `frontend/src/App.jsx` — основной компонент приложения.
- `frontend/src/components/Tuner.jsx` — экран тюнера.
- `frontend/src/components/UserTracks.jsx` — экран библиотеки и авторизации.
- `frontend/src/components/TrackPage.jsx` — экран отдельного трека.
- `frontend/src/components/AdminComments.jsx` — экран админа.
- `frontend/src/hooks/useTuner.js` — логика работы с микрофоном и WebSocket.

### Где хранится токен в браузере

Токен сохраняется в `localStorage` браузера как `user_token`.

Каждый раз, когда фронтенд делает защищенный запрос, он добавляет заголовок:

```
Authorization: Bearer <token>
```

Если токен отсутствует или истек, запрос получает ошибку.

## Как устроены данные

### Что такое таблица?

Таблица — это место в базе данных для хранения похожих записей.

Например, таблица `users` хранит всех пользователей.

### Какие таблицы есть в проекте

#### В `user-service`

- `users` — пользователи.
- `roles` — роли `user` и `admin`.
- `tokens` — токены авторизации.
- `tracks` — треки, созданные пользователями.
- `genres` — музыкальные жанры.
- `track_genres` — связь треков и жанров.
- `favorites` — избранные треки.

#### В `catalog-service`

- `tunings` — настройки струн гитары.
- `songs` — демонстрационные песни и их тюнинги.

#### В `comment-service`

- `comments` — комментарии к трекам.

### Как данные связаны между собой

- каждый трек в `tracks` принадлежит пользователю (`owner_id`);
- трек может иметь несколько жанров через `track_genres`;
- пользователь может отмечать треки как любимые в `favorites`;
- комментарий привязан к треку по `track_id`;
- ответ на комментарий хранится через `parent_id`.

## Краткие ответы на «что это такое»

### Что такое `WebSocket`?

Это способ связаться с сервером, сохранив открытое соединение. Его удобно использовать, когда данные поступают постоянно.

### Что такое `HTTP`?

Это стандартный способ обмена запросами между браузером и сервером. Подходит для большинства задач, где запрос выполняется один раз.

### Что такое `токен`?

Это длинная случайная строка, которую сервер выдает после входа. Токен используется вместо пароля для дальнейших запросов.

### Что такое `авторизация`?

Проверка, может ли пользователь выполнять действие. Например, удалять комментарии может только админ.

### Что такое `аутентификация`?

Проверка, кто вы. Обычно это логин и пароль.

### Что такое `ORM` и `SQLAlchemy`?

**ORM** — это библиотека, которая позволяет работать с базой данных как с обычными объектами Python.

`SQLAlchemy` — одна из таких библиотек. Она переводит Python-объекты в записи базы данных.
